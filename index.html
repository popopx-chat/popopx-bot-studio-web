01 / CAPABILITIES

An agent workbench, checked against the engine source

The five blocks people ask about first, each labelled with what is actually built behind the name today. Every claim here was read against the engine repository before it was published.

Released means the named capability works end to end today. In beta means the headline works but half the name is missing. Planned means there is no code behind it yet.

The loop, step by step

  1. 1

    Create the agent

    A new bot gets its own row, its own token, its own popopx-cli process, its own cli-data directory and its own control port on 5230 and up.

    Released
  2. 2

    Configure model and rules

    Reply rules, routing rules and one system prompt per bot. The model is any OpenAI-compatible chat endpoint, and the default is a local Ollama on loopback. There is no provider registry yet.

    In beta
  3. 3

    Connect controlled tools

    An inbound webhook turns an external alert into a bot message; the relay turns a reply back into a signed call to your own endpoint. What is not here is the model deciding to call a tool by itself.

    In beta
  4. 4

    Test in the sandbox

    Preview a rule or a routing plan against a test chat before it is saved, run each bot in its own isolated process, and keep the offline self-test as the gate.

    Released
  5. 5

    Publish and connect to Chat

    Provisioning hands back the permanent contact address and a QR code you can put anywhere. There is no separate publish button and no staged rollout: the address exists once the bot exists.

    Released
Planned

Agent definition and version management

Defining an agent is released: one record per bot with its own sandbox, token and data directory, plus a cold-backup bundle that carries it to another host. Version management is not: there is no revision history, no publish state and no rollback.

In beta

Multiple model providers

One OpenAI-compatible call is released, and any vendor that speaks that shape works, including a model you host yourself. What is missing is a registry of providers: today it is one base URL, one model name and one key per bot.

In beta

System prompt and role orchestration

Each bot has one editable system prompt, injected as the system message of every model call. Multi-role orchestration, one persona per channel or per stage of a conversation, is not implemented.

Planned

Tool calling with permission isolation

Not implemented. The engine has no tool-calling path and no enforced permission model: the scope a plugin declares is metadata, and the dispatcher orders plugins by priority alone.

In beta

Run logs and replay monitoring

The message ledger, the per-bot log view and the live updates ring are released and readable in the console. Replay, stepping a conversation back through a run, is not.

Released

Multi-bot sandbox factory

Every bot gets its own popopx-cli process, its own cli-data directory, its own control port and its own SQLite files, started and stopped from one screen.

  • run-cli.sh
  • cli.pid
  • cli-data/
  • ports 5230+
Released

Routing and tickets

Forward enquiries into a support group with a #T ticket id; an operator answers with the ticket id and the reply goes back to the customer.

  • Routing
  • #T-0001 → Auto-reply
  • 24/7 agent desk
Released

Permanent address

Each bot gets its own CLI data directory and permanent contact link, so reconnecting users always reach the same bot.

Released

No-code rules

Match a keyword, exact phrase or regular expression and reply with a template. Cooldown keeps a chatty user from being spammed.

Released

Private key and local sovereignty

The identity key, the ledger and every message log live in files you own with mode 0600. There is no cloud account to lose and no vendor holding a copy.

02 / USE CASES

Four flows that already run

Each of these is the engine's own behaviour on the day you install it, not a plan: what you can build in the console before the first restart.

Released

Support desk with tickets

Rules answer the common questions, anything unmatched is forwarded into a support group under a #T ticket, and an operator's reply goes back to that one customer.

Released

Alert relay for on-call

A monitoring webhook arrives as a bot message in the right group; the human answer leaves again as a signed callback to your own endpoint, with the ticket id attached.

Released

Internal automation

Any script on the same host calls sendMessage with the bot token over loopback, or polls getUpdates, so deploys, queues and cron jobs arrive in chat instead of in a log file.

Released

A contact address that never changes

The permanent address and its QR code come from key material on your own disk, so moving the data directory to another machine keeps the same reachable identity, and no provider can take the account away.

03 / INTEGRATIONS

What plugs in, and how

Five surfaces the engine exposes today, the plugins that sit on them, and the one integration everybody asks for that is still missing.

Released

OpenAI-compatible model endpoint

POST to {base_url}/chat/completions with a Bearer key. Any vendor that speaks the OpenAI shape works; the default is Ollama on 127.0.0.1:11434, and a per-bot switch refuses anything but loopback.

Released

Signed webhooks in and out

Inbound alerts become messages; outbound callbacks carry an HMAC-SHA256 signature with an auto-generated secret. Targets are restricted to https or to loopback http.

Released

Telegram-shaped Open API

getMe, sendMessage, setWebhook and getUpdates on the same loopback port as the console, addressed by bot token.

Released

Plugin bus

Four built-in plugins on one priority chain, with room for your own module that replies, forwards or stays silent.

Planned

Model-initiated tool calling

Not implemented: nothing lets the model call a tool by itself. Today a tool runs because a rule, a plugin or your own code invokes it.

The POPOPX ecosystem

Four portals on four subdomains of one domain, each a product of its own. This page is the one for the agent workbench.

The four portals share one domain and link to each other, and this page loads nothing from the other three. The dashed edges above, taking a task from POPOPX Chat, calling Service Suite, or dispatching compute to Mac Node, are not implemented in this repository yet. Mac Node does publish a loopback job API; Bot Studio does not call it.

Plugins

  1. auto_reply Layered Q&A and command menus Answers from a keyword table, offers a numbered menu and falls back to a human handoff.
  2. msg_router Cross-chat and cross-group routing Aggregates alerts, mirrors a direct message into a group and keeps the ticket id attached.
  3. llm_bridge OpenAI-compatible assistant Point it at any compatible base URL, set the model, and the bridge asks only when a rule did not match.
  4. webhook_relay Inbound alerts and outbound callbacks Turns an external monitor webhook into a bot message, and a customer reply into your own webhook call.

04 / DOCS

Install and first run

Four paths, the same engine: a production Linux box, a Mac you keep running, a development checkout, or the three clicks inside the console.

Installs Python 3.11, creates a system user, writes a systemd unit and pulls popopx-cli for your architecture.

sudo apt update && sudo apt install -y git python3.11-venv
git clone https://github.com/popopx-chat/popopx-bot-studio.git
cd popopx-bot-studio

./install_ubuntu22.sh --dry-run          # plan only, nothing written
sudo ./install_ubuntu22.sh --mode native

systemctl status popopx-bot-studio
sudo -u popopx-studio cat /etc/popopx-bot-studio/.env
  • Open the console through a reverse proxy on your own host: the engine binds 127.0.0.1:8090 and never 0.0.0.0.
  • Flags: --check validates the host, --mode native installs in place, --dry-run prints the plan, --uninstall removes the service and keeps your data.

Registers a launchd agent so the studio comes back after a reboot, using the same installer flags as Linux.

git clone https://github.com/popopx-chat/popopx-bot-studio.git
cd popopx-bot-studio

./install_macos.sh --check               # report what would change
./install_macos.sh                       # launchd agent + venv
./install_macos.sh --lan                 # bind a LAN address on purpose

launchctl list | grep popopx
open http://127.0.0.1:8090
  • Every bot is launched through a wrapper script so launchd cannot split the arguments it passes to popopx-cli.
  • Backups and the SQLite ledger stay under var/studio, so one archive of that folder is a complete restore point.

No system service, no sudo: a virtualenv on your laptop with the console on loopback port 8090.

./start_macos.sh                         # venv + 127.0.0.1:8090

STUDIO_ADMIN_TOKEN=dev-token \
STUDIO_DATA_DIR=$PWD/var/studio \
BOT_WS_PORT_BASE=5230 BOT_WS_PORT_MAX=5299 \
python3 -m uvicorn studio.app.main:app --port 8090
  • The engine ships an offline self-test of 1,884 assertions in 15 groups; it needs no network and no real contacts.
  • Without STUDIO_ADMIN_TOKEN every admin route answers 401, so an unconfigured checkout cannot be driven by accident.

Three moves in the console, then the Open API is yours.

  1. 1

    Install popopx-cli from the official releases (checksum verified) and start the studio.

  2. 2

    Create a bot in the console, pick its SMP servers and read the permanent address or QR code.

  3. 3

    Describe your support flow: add reply rules and a routing rule that targets the group.

  4. 4

    Call the Open API with the bot token, or let a plugin take over the conversation.

  • The bot token is minted locally and stored only in the SQLite ledger; rotate it by re-creating the credential in the console.

05 / OPEN API

A Telegram-shaped API on an isolated network

Call sendMessage with the bot token, register a webhook, or poll getUpdates. The admin console and the API share one engine and one loopback port.

Send a message

Reply to any contact or group the bot already reaches.

curl -X POST http://127.0.0.1:8090/bot$BOT_TOKEN/sendMessage \
  -H "content-type: application/json" \
  -d '{"chat_ref":"<contact>","text":"Deploy finished."}'

Register a webhook

Push inbound events to your own endpoint instead of polling.

curl -X POST http://127.0.0.1:8090/bot$BOT_TOKEN/setWebhook \
  -d '{"url":"https://intranet.local/hooks/popopx"}'

Poll for updates

Read the ring buffer behind the gateway, newest last.

curl "http://127.0.0.1:8090/bot$BOT_TOKEN/getUpdates?limit=50"

Tokens and admin credentials are read from .env on your host; the site never sends anything anywhere.

The permission boundary, item by item

Released

Where the keys live

STUDIO_ADMIN_TOKEN is read from the environment or .env and compared in constant time. Bot tokens and the model API key stay in the SQLite ledger on your disk and are masked in every API response. At rest the ledger is not encrypted: the 0600 file mode, the 0700 data directory and the loopback bind are what protect it. Only cold-backup bundles are encrypted, with AES-GCM under a key derived by scrypt.

Planned

Capability tokens

Not implemented. A plugin declares a scope field today, but the dispatcher never checks it and orders plugins by priority alone: there is no grant, no expiry and no per-tool permission decision.

In beta

Audit trail

Messages, rule hits, plugin errors and webhook changes are written to the ledger and readable in the console. Admin actions do not yet have their own audit table, and there is no export format for an auditor.

Planned

Revoking access

Today you revoke by editing .env and restarting, or by clearing a bot's webhook target in the console. A self-service revoke or rotate endpoint, and the grant list that would go with it, are not implemented.

07 / FAQ

Questions before the first install

Licence, agents, migration and the difference to a commercial service account.

Can I use this commercially under AGPL-3.0-only?

Yes. AGPL-3.0 obliges you to share the source of the studio itself when you offer a modified version over a network, including changes to the engine and the plugins. Your bots, rules, reply texts and message data are your content and are not affected. The licence text is in the repository root.

How do several human agents work the same queue?

Routing forwards an enquiry into a support group with a #T ticket id and the bot keeps the original chat reference. Any agent replies with that ticket id, and the engine sends the answer back to the customer only. Every hand is written to the audit log with the actor and the timestamp.

How do I move a running bot to another server?

Export a bundle from the cold-backup screen: the bot is stopped, its cli-data directory, keys and settings are packed, and the bot starts again. Copy the archive to the new host, restore it, and the permanent contact address stays the same because identity lives in those files, not in a vendor account. Restoring is lossless and idempotent: a user already inside cli-data is detected and reused instead of recreated, so the original permanent contact link survives every restart.

How is this different from a commercial service account?

A service account is a rented identity: the provider issues the token, keeps the message graph, sets the rate limits and can end the account. The studio issues the token itself, keeps the ledger on your disk and has no account to close. The trade is that you own the uptime, the backups and the updates.

Why does it only listen on 127.0.0.1?

The console and the Open API carry an admin token, so an exposed port is the most likely way in. The engine validates the bind address at start-up and refuses a non-loopback host unless you set STUDIO_ALLOW_LAN=1 on purpose. Put Caddy or nginx in front, keep the port closed and add TLS plus your own authentication there.

Does the download of popopx-cli leak anything?

No binary is committed to the repository, because the AGPL licence and the download both point at the official releases. The installer fetches the archive for your operating system and architecture, verifies the SHA-256 checksum, then unpacks it into the data directory. Nothing about your bots is part of that request.

08 / ROADMAP

What is not built yet

The gaps this page had to mark as planned, written down in one place so nothing is implied by a picture.

Planned

Tool calling with per-tool scopes

The model would call declared tools, with a scope check enforced in the dispatcher instead of the priority-only ordering that exists now.

Planned

Capability tokens and revocation

Short-lived grants per bot and per tool, with an explicit revoke endpoint that replaces editing .env by hand and restarting.

Planned

Agent versions and rollback

A revision history for the agent definition, a publish state separate from the runtime state, and rollback to a named revision. Today only the cold-backup bundle moves between hosts.

Planned

Model provider registry

Named vendors with their own keys, quotas and health checks behind the OpenAI-compatible call, instead of one base URL per bot.

Planned

Replay and admin audit

A persisted event stream you can scrub back through, and a table of who changed what in the console.

Planned

Ecosystem call paths

Handing a task from POPOPX Chat to an agent, calling Service Suite, or dispatching local compute to a Mac Node: the receiving halves exist on those sides, the calling half does not exist here.

This list is measured against the engine source, not promised on a calendar: none of it has a date. The engine reports version 1.0.0 but has no published tag or Release yet, so installation stays clone-and-run, and every status badge on this page reflects the code at the commit the source repository points at.

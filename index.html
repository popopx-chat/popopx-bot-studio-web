An agent workbench, checked against the engine source

The blocks people ask about first, each labelled with what is actually built behind the name today. Every claim here was read against the engine repository before it was published.

Released means the named capability works end to end today. In beta means the headline works but half the name is missing. Planned means there is no code behind it yet.

The loop, step by step

  1. 1

    Create the agent

    A new bot gets its own row, its own token, its own popopx-cli process, its own cli-data directory and its own control port on 5230 and up.

    Released
  2. 2

    Configure model and rules

    Reply rules, routing rules and one system prompt per bot. The model is any OpenAI-compatible chat endpoint, and the default is a local Ollama on loopback. There is no provider registry yet.

    In beta
  3. 3

    Connect controlled tools

    An inbound webhook turns an external alert into a bot message; the relay turns a reply back into a signed call to your own endpoint. Needle 3 also extracts one of five read-only tool intents from a sentence, but nothing executes a tool on the model's behalf.

    In beta
  4. 4

    Test in the sandbox

    Preview a rule or a routing plan against a test chat before it is saved, run each bot in its own isolated process, and keep the offline self-test as the gate.

    Released
  5. 5

    Publish and connect to Chat

    Provisioning hands back the permanent contact address and a QR code you can put anywhere. If an address fits the codec but exceeds the 1,663 bytes a version-40 QR can carry, the console says so with a 409 and a diagnostic drawer instead of drawing a broken image.

    Released
Planned

Agent definition and version management

Defining an agent is released: one record per bot with its own sandbox, token and data directory, plus a cold-backup bundle that carries it to another host. Version management is not: there is no revision history, no publish state and no rollback.

In beta

Multiple model providers

One OpenAI-compatible call is released, and any vendor that speaks that shape works, including a model you host yourself. What is missing is a registry of providers: today it is one base URL, one model name and one key per bot.

In beta

System prompt and role orchestration

Each bot has one editable system prompt, injected as the system message of every model call. The process-local orchestrator can lend a read-only capability to a sibling bot, but one persona per channel or per stage of a conversation is still not implemented.

In beta

Tool calling with permission isolation

Partly implemented. Needle 3 extracts one of five read-only tool intents (calendar availability, propose create/reschedule/cancel, workspace summarize) and never executes a write; a grant table governs which bot may borrow which read-only capability. Model-initiated execution with a per-tool scope check in the dispatcher is still missing.

In beta

Run logs and replay monitoring

The message ledger, the per-bot log view and the live updates ring are released, and orch/replay returns a whole dispatch chain by correlation id. Stepping a chat conversation back through a run is still not implemented.

Released

Multi-bot sandbox factory

Every bot gets its own popopx-cli process, its own cli-data directory, its own control port from 5230 to 5299 and its own SQLite files, started and stopped from one screen.

  • run-cli.sh
  • cli.pid
  • cli-data/
  • ports 5230+
Released

Routing and tickets

Forward enquiries into a support group with a #T ticket id; an operator answers with the ticket id and the reply goes back to the customer.

  • Routing
  • #T-0001 → Auto-reply
  • 24/7 agent desk
Released

Permanent address

Each bot gets its own CLI data directory and permanent contact link, so reconnecting users always reach the same bot.

Released

No-code rules

Match a keyword, exact phrase or regular expression and reply with a template. Cooldown keeps a chatty user from being spammed.

Released

Private key and local sovereignty

The identity key, the ledger and every message log live in files you own with mode 0600. There is no cloud account to lose and no vendor holding a copy.

02 / AGENTS

One process, a team of agents

Each bot keeps its own rules, model key, timezone and calendar cache inside one studio process; a default-deny orchestrator lets one agent borrow what a sibling knows without handing over a single write.

created → authorized → scheduled → allocated → running → awaiting_user → completed → workspace_cleanup or failed cancelled refused

The orchestration state machine in schema v7: eight stages from created to workspace_cleanup, and one terminal branch for failed, cancelled and refused.

Released

A 24/7 personal agent that only proposes

Needle 3 is a 33.7 MiB weight file shipped with the repository. It extracts one of five calendar or workspace intents in milliseconds, and a deterministic extractor takes over when the native runtime is missing. Working hours, buffers, blocked periods and keywords per bot decide what counts as free, and every rejected slot keeps a readable reason in the audit log. The calendar is never written until the owner confirms the card.

  • needle3.cact
  • 33.7 MiB
  • 5 intents
  • confirm first
Released

Process-local multi-agent orchestration

One bot borrows a read-only capability from a sibling — compose a reply, plan a route, mask availability, summarize a workspace or profile the ledger — inside the same studio process. There is no new port, no direct SMP call and no write to another bot's rules. Hops are capped at 3, concurrency at 32, each task times out between 0.5 and 300 seconds, and fan-out is capped at 8 targets.

  • 5 read-only tools
  • hops ≤ 3
  • 32 concurrent
  • fan-out ≤ 8
Released

Grants are denied by default

A dispatch needs an explicit (origin, target, capability) row in agent_task_grants; the wildcard target must be created on purpose, and every row can be toggled or deleted. Each task lands in SQLite schema v7 with a correlation id, duration, result summary and a stable reason code that orch/replay can reconstruct; the eleven stored statuses run from created to workspace_cleanup, with failed, cancelled and refused as terminal branches.

  • agent_task_grants
  • default deny
  • schema v7
  • correlation_id
Released

Masked A2A negotiation and zero-install booking

Two paired personal agents exchange only start, end, tz, free and ref over their existing SMP session key, signed and replay-protected; titles, attendees and notes cannot leave. A guest books through a one-time /book/{token} HMAC link with no session, no cookie and no script, in all 21 languages, and the .ics invitation exists only after the owner approves.

  • start · end · tz
  • free · ref
  • /book/{token}
  • 21 languages

Every path above stays on 127.0.0.1. The only outbound calls are to your own model endpoint, a paired agent's SMP queue, or the Mac Node bridge on http://127.0.0.1:18920.

Released

Nine stages over eleven stored statuses

The engine writes eleven statuses to SQLite schema v7. The board draws them as nine stages: the eight steps a dispatch walks, plus one terminal branch that collects failed, cancelled and refused.

  1. 1
    created

    The row is written first, with its correlation id, isolation profile and retention mode. Nothing has run yet.

  2. 2
    authorized

    The grant for origin, target and capability is found and enabled. A policy refusal lands as its own refused row before this point, never as an error code alone.

  3. 3
    scheduled

    The timeout is fixed here, between 0.5 and 300 seconds: the tighter of the grant and the profile wins.

  4. 4
    allocated

    Isolation is attached: a separate process or the target bot's own sandbox, with 32 concurrent tasks across the engine.

  5. 5
    running

    The capability executes in the target's sandbox. A fan-out beyond 8 targets is refused with the fanout_limit reason code.

  6. 6
    awaiting_user

    If the grant or the profile requires approval, the task parks here and posts a task card. The owner's callback resumes it, and approval never skips the grant check that already passed.

  7. 7
    completed

    The result summary and latency are written. Under zero retention the body is replaced before this row exists.

  8. 8
    workspace_cleanup

    The workspace is erased, an ephemeral result is cleared with result_purged, and the task ends in workspace_cleanup.

  9. 9
    failed · cancelled · refused

    Failed, cancelled and refused share one branch because none of them proceeds. The row keeps a stable reason code, and the audit keeps no text.

Released

Approval cards gate every write

A task that needs a write parks in awaiting_user and posts a task card to the chat. An ok callback resumes it, a no callback writes cancelled with the declined reason, and an alt callback only records the choice.

  • popopx.agent.task.v1
  • ::CB::ppxok_
  • ::CB::ppxno_
  • ::CB::ppxalt_
Released

ZDR

Zero retention, per task

Zero retention is a switch on the task, not a promise about the model call: whatever the model returned, the stored result is the redaction marker.

Retention modes

  • zero_retention

    The result body is replaced by a redaction marker before it is stored, so the ledger keeps that the task ran and nothing it produced.

    {"redacted": true, "retention_mode": "zero_retention"}
  • ephemeral

    The result is stored for the length of the task, then cleared at workspace_cleanup; the cleanup detail records result_purged.

  • user_owned

    The default. The result stays in the workspace you own until you delete it.

Audit rows carry ids, counters and reason codes

Each transition records the task id, origin, target, capability, hops, latency and a stable reason code. Prompts, results and message text never reach the audit table.

orchestrator completed bot=billing target=ops cap=workspace.summarize task=tk_7f3a hops=1 latency_ms=1840 detail=ok
orchestrator declined  bot=billing target=ops cap=reply.compose        task=tk_9d22 hops=1 latency_ms=0    detail=declined
orchestrator refused   bot=desk    target=ops cap=reply.compose        task=tk_c410 hops=1 latency_ms=0    detail=no_grant

Both panels follow the engine at SQLite schema v7 and the Mac Node's two compute profiles; the limits shown are policy ceilings, not a benchmark.

Released

05 / INTEGRATIONS

What plugs in, and how

Five surfaces the engine exposes today, the plugins that sit on them, and the one integration everybody asks for that is still missing.

Released

OpenAI-compatible model endpoint

POST to {base_url}/chat/completions with a Bearer key. Any vendor that speaks the OpenAI shape works; the default is Ollama on 127.0.0.1:11434, and a per-bot switch refuses anything but loopback.

Released

Signed webhooks in and out

Inbound alerts become messages; outbound callbacks carry an HMAC-SHA256 signature with an auto-generated secret. Targets are restricted to https or to loopback http.

Released

Telegram-shaped Open API

getMe, sendMessage, setWebhook and getUpdates under /api/v1 on the same loopback port as the console, addressed by bot token.

Released

Plugin bus

Five built-in plugins on one priority chain, the 24/7 personal agent included, with room for your own module that replies, forwards or stays silent.

Planned

Model-initiated tool calling

Not implemented: Needle 3 can extract one of five read-only tool intents from a sentence, but nothing executes a tool on the model's own authority. A tool runs because a rule, a plugin or your own code invokes it.

The POPOPX ecosystem

Four portals on four subdomains of one domain, each a product of its own. This page is the one for the agent workbench.

Plugins

06 / DOCS

Install and first run

Four paths, the same engine: a production Linux box, a Mac you keep running, a development checkout, or the three clicks inside the console.

Installs Python 3.11, creates a system user, writes a systemd unit and pulls popopx-cli for your architecture.

sudo apt update && sudo apt install -y git python3.11-venv
git clone https://github.com/popopx-chat/popopx-bot-studio.git
cd popopx-bot-studio

./install_ubuntu22.sh --dry-run          # plan only, nothing written
sudo ./install_ubuntu22.sh --mode native

systemctl status popopx-bot-studio
sudo -u popopx-studio cat /etc/popopx-bot-studio/.env
  • Open the console through a reverse proxy on your own host: the engine binds 127.0.0.1:8090 and never 0.0.0.0.
  • Flags: --check validates the host, --mode native installs in place, --dry-run prints the plan, --uninstall removes the service and keeps your data.

Registers a launchd agent so the studio comes back after a reboot, using the same installer flags as Linux.

git clone https://github.com/popopx-chat/popopx-bot-studio.git
cd popopx-bot-studio

./install_macos.sh --check               # report what would change
./install_macos.sh                       # launchd agent + venv
./install_macos.sh --lan                 # bind a LAN address on purpose

launchctl list | grep popopx
open http://127.0.0.1:8090
  • Every bot is launched through a wrapper script so launchd cannot split the arguments it passes to popopx-cli.
  • Backups and the SQLite ledger stay under var/studio, so one archive of that folder is a complete restore point.

No system service, no sudo: a virtualenv on your laptop with the console on loopback port 8090.

./start_macos.sh                         # venv + 127.0.0.1:8090

STUDIO_ADMIN_TOKEN=dev-token \
STUDIO_DATA_DIR=$PWD/var/studio \
BOT_WS_PORT_BASE=5230 BOT_WS_PORT_MAX=5299 \
python3 -m uvicorn studio.app.main:app --port 8090
  • The engine ships an offline self-test of 10,572 assertions in 26 groups; it needs no network and no real contacts.
  • Without STUDIO_ADMIN_TOKEN every admin route answers 401, so an unconfigured checkout cannot be driven by accident.

Four moves in the console, then the Open API is yours.

  1. 1

    Install popopx-cli from the official releases (checksum verified) and start the studio.

  2. 2

    Create a bot in the console, pick its SMP servers and read the permanent address or QR code.

  3. 3

    Describe your support flow: add reply rules and a routing rule that targets the group.

  4. 4

    Call the Open API with the bot token, or let a plugin take over the conversation.

  • The bot token is minted locally and stored only in the SQLite ledger; rotate it by re-creating the credential in the console.

07 / OPEN API

A Telegram-shaped API on an isolated network

Call sendMessage with the bot token, register a webhook, or poll getUpdates. The admin console and the API share one engine and one loopback port.

Send a message

Reply to any contact or group the bot already reaches.

curl -X POST http://127.0.0.1:8090/api/v1/bot$BOT_TOKEN/sendMessage \
  -H "content-type: application/json" \
  -d '{"chat_ref":"@7","text":"Deploy finished."}'

Register a webhook

Push inbound events to your own endpoint instead of polling.

curl -X POST http://127.0.0.1:8090/api/v1/bot$BOT_TOKEN/setWebhook \
  -H "content-type: application/json" \
  -d '{"url":"https://intranet.local/hooks/popopx"}'

Poll for updates

Read the ring buffer behind the gateway, newest last.

curl "http://127.0.0.1:8090/api/v1/bot$BOT_TOKEN/getUpdates?limit=50"

Tokens and admin credentials are read from .env on your host; the site never sends anything anywhere.

The permission boundary, item by item

Released

Where the keys live

STUDIO_ADMIN_TOKEN is read from the environment or .env and compared in constant time. Bot tokens and the model API key stay in the SQLite ledger on your disk and are masked in every API response. At rest the ledger is not encrypted: the 0600 file mode, the 0700 data directory and the loopback bind are what protect it. Only cold-backup bundles are encrypted, with AES-GCM under a key derived by scrypt.

In beta

Capability tokens

Partly implemented. agent_task_grants decides which bot may borrow which read-only capability: default-deny, wildcard target only on purpose, with hop and concurrency caps. What is missing is a per-tool scope in the plugin dispatcher, which still runs plugins by priority and checks no scope field.

In beta

Audit trail

Messages, rule hits, plugin errors, webhook changes, orchestrator tasks and A2A or guest actions are written to the ledger and readable in the console. Admin actions do not yet have their own audit table, and there is no export format for an auditor.

In beta

Revoking access

Orchestrator grants can be toggled off or deleted from the console, and a webhook target can be cleared there. Admin and bot tokens still rotate by editing .env and restarting; there is no self-service rotate or revoke endpoint.

09 / FAQ

Questions before the first install

Licence, agents, migration and the difference to a commercial service account.

Can I use this commercially under AGPL-3.0-only?

Yes. AGPL-3.0 obliges you to share the source of the studio itself when you offer a modified version over a network, including changes to the engine and the plugins. Your bots, rules, reply texts and message data are your content and are not affected. The licence text is in the repository root.

How do several human agents work the same queue?

Routing forwards an enquiry into a support group with a #T ticket id and the bot keeps the original chat reference. Any agent replies with that ticket id, and the engine sends the answer back to the customer only. Every hand is written to the audit log with the actor and the timestamp.

How do I move a running bot to another server?

Export a bundle from the cold-backup screen: the bot is stopped, its cli-data directory, keys and settings are packed, and the bot starts again. Copy the archive to the new host, restore it, and the permanent contact address stays the same because identity lives in those files, not in a vendor account. Restoring is lossless and idempotent: a user already inside cli-data is detected and reused instead of recreated, so the original permanent contact link survives every restart.

How is this different from a commercial service account?

A service account is a rented identity: the provider issues the token, keeps the message graph, sets the rate limits and can end the account. The studio issues the token itself, keeps the ledger on your disk and has no account to close. The trade is that you own the uptime, the backups and the updates.

Why does it only listen on 127.0.0.1?

The console and the Open API carry an admin token, so an exposed port is the most likely way in. The engine validates the bind address at start-up and refuses a non-loopback host unless you set STUDIO_ALLOW_LAN=1 on purpose. Put Caddy or nginx in front, keep the port closed and add TLS plus your own authentication there.

Does the download of popopx-cli leak anything?

The CLI is not committed: the installer fetches the archive for your operating system and architecture from the official releases, verifies the SHA-256 checksum, then unpacks it into the data directory. The repository does ship the Needle 3 weight file (33.7 MiB) so the agent works without a download; it contains no personal data, and nothing about your bots is part of any request.

10 / ROADMAP

What is not built yet

The gaps this page had to mark as planned, written down in one place so nothing is implied by a picture.

Planned

Tool calling with per-tool scopes

The model would call declared tools, with a scope check enforced in the dispatcher instead of the priority-only ordering that exists now. Needle 3 today extracts the intent but never executes it.

Planned

Capability tokens and revocation

Short-lived grants per bot and per tool with expiry, plus a revoke endpoint for admin and bot tokens that replaces editing .env by hand and restarting.

Planned

Agent versions and rollback

A revision history for the agent definition, a publish state separate from the runtime state, and rollback to a named revision. Today only the cold-backup bundle moves between hosts.

Planned

Model provider registry

Named vendors with their own keys, quotas and health checks behind the OpenAI-compatible call, instead of one base URL per bot.

Planned

Replay and admin audit

A persisted event stream you can scrub back through, and a table of who changed what in the console.

Planned

Ecosystem call paths

Handing a task from POPOPX Chat to an agent, calling Service Suite, or dispatching local compute to a Mac Node: the receiving halves exist on those sides, the calling half does not exist here.

This list is measured against the engine source, not promised on a calendar: none of it has a date. The engine reports version 1.0.0 but has no published tag or Release yet, so installation stays clone-and-run, and every status badge on this page reflects the code at the commit the source repository points at.
